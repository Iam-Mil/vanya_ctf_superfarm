# SECURE.md — защита своих машин: пароли, SSH-ключи (гайд)

Зачем это вообще нужно: завтра все команды получат **одинаковые** вулнбоксы
и, скорее всего, **одинаковый стартовый пароль**. Пока вы его не сменили —
любая команда может зайти на ваш бокс по SSH и сделать что угодно. Ниже —
как закрыть эту дыру за 5 минут.

---

## 1. Быстрый путь: скрипт (рекомендуется)

На **каждой** своей машине (вулнбокс и Kali каждого человека):

```bash
sudo ./secure.sh --gen-key
# что сделал: сменил пароль (напечатал его — ЗАПИШИ в чат команды),
#             создал новую пару ключей (приватник напечатан — забери на Kali),
#             вычистил чужие ключи из authorized_keys (старое — в бэкап)

# ЗАТЕМ проверь вход по ключу из ДРУГОГО терминала (эту сессию не закрывай!):
ssh -i ~/.ssh/ctf_ed25519 <юзер>@<ip_машины>

# ключ заходит? докручиваем пункт чек-листа «отключить вход по паролю»:
sudo ./secure.sh --strict
```

Если у тебя уже есть ключ на Kali (генерили вечером) — вместо `--gen-key`:

```bash
sudo ./secure.sh --pubkey ~/.ssh/id_ed25519.pub
```

По умолчанию скрипт оставляет **два способа входа**: по ключу и по новому
паролю — запереть себя невозможно. `--strict` отключает пароль только после
того, как сам проверил, что ключ работает.

## 2. Ручной путь: если скрипт не работает

Каждый шаг скрипта делается руками. Иди по порядку, не пропускай проверку.

### Шаг 1. Сменить пароль

```bash
passwd
# спросит текущий пароль, затем дважды новый
```

- Придумай **длинный** (20+ символов, можно просто набор слов/цифр —
  угадать его никто не сможет).
- **Сразу запиши его в чат команды** — с другой машины ты его не достанешь.
- Проверка: не закрывая эту сессию, открой второй терминал и зайди по
  новому паролю. Зашёл — ок.

### Шаг 2. Добавить свой SSH-ключ

Если ключа на Kali ещё нет — сгенерируй **на своей Kali** (не на боксе):

```bash
ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519
# -t ed25519 — современный тип ключа
# -N ""     — без парольной фразы (чтобы входить без вопросов)
# -f ...    — куда сохранить
```

Теперь **публичную** часть (файл `.pub` — её можно показывать всем)
передай на защищаемую машину. Два способа:

```bash
# способ А — одной командой с твоей Kali (ssh-copy-id сам всё скопирует):
ssh-copy-id -i ~/.ssh/id_ed25519.pub <юзер>@<ip_машины>

# способ Б — руками, на защищаемой машине:
mkdir -p ~/.ssh                      # создать папку, если нет
chmod 700 ~/.ssh                      # доступ только тебе
echo "ssh-ed25519 AAAA...твой_публичный_ключ" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys      # доступ только тебе
```

**Проверка (обязательно, прежде чем идти дальше):**

```bash
ssh -i ~/.ssh/id_ed25519 <юзер>@<ip_машины>
# зашло БЕЗ пароля? отлично. Сессию не закрывай, пока всё не доделаешь.
```

Если просит пароль — смотри §3 «ключ не заходит».

### Шаг 3. Удалить чужие ключи

В `~/.ssh/authorized_keys` может лежать оргский/тестовый ключ — всех,
кроме ваших, надо убрать. Сначала бэкап, потом чистка:

```bash
cp ~/.ssh/authorized_keys ~/.ssh/authorized_keys.bak   # страховка
echo "ssh-ed25519 AAAA...твой_ключ" > ~/.ssh/authorized_keys
# ↑ ПЕРЕЗАПИСАЛИ файл только своим ключом (> вместо >> — это важно)
chmod 600 ~/.ssh/authorized_keys
```

Хочешь добавить ключи нескольких людей команды — повтори `echo ... >>`
(уже с двумя `>>`, добавление) для каждого.

**Проверка:** зайди по ключу ещё раз — должно работать. Если сломалось:
`cp ~/.ssh/authorized_keys.bak ~/.ssh/authorized_keys` — и всё вернулось.

### Шаг 4. Отключить вход по паролю

⚠️ Делай ТОЛЬКО после того, как вход по ключу проверен. Иначе, если ключ
что-то сломает, ты запрёшь сам себя.

```bash
sudo mkdir -p /etc/ssh/sshd_config.d
sudo tee /etc/ssh/sshd_config.d/10-strict.conf > /dev/null <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
EOF

sudo sshd -t        # проверка конфига: молчит = всё ок (ошибка = НЕ перезапускай!)
sudo systemctl restart ssh
```

**Проверка:** из другого терминала попробуй зайти **по паролю** — должно
пишет «Permission denied (publickey)». А по ключу — пускать как раньше.
Если по паролю всё ещё пускает — смотри §3.

## 3. Если что-то не работает — разбор по симптомам

### «Ключ не заходит, просит пароль»

По порядку проверь на **защищаемой** машине:

```bash
ls -ld ~/.ssh                 # права должны быть drwx------ (700)
ls -l ~/.ssh/authorized_keys  # права должны быть -rw------- (600)
whoami                        # файлы принадлежат этому юзеру?
cat ~/.ssh/authorized_keys    # твой ключ там ЕСТЬ и в одну строку?
```

Чинится:

```bash
chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys
sudo chown -R $USER:$USER ~/.ssh
```

Смотри подробный лог со своей Kali — он скажет причину сам:

```bash
ssh -v -i ~/.ssh/id_ed25519 <юзер>@<ip_2>&1 | grep -iE "denied|offer|accept"
```

### «По паролю всё ещё пускает (хотя отключал)»

На большинстве систем настройки лежат в двух местах — проверь оба:

```bash
sudo grep -rn "PasswordAuthentication" /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
# где-нибудь стоит yes ПОСЛЕ твоего no — ssh читает ПЕРВОЕ значение,
# файлы из sshd_config.d имеют приоритет, но внутри файла важен порядок
sudo systemctl restart ssh
```

### «sshd не перезапускается / sshd -t ругается»

Не паникуй и НЕ выходи из сессии — пока сессия жива, ты внутри.
Посмотри, на что ругается:

```bash
sudo sshd -t          # покажет строку с ошибкой
```

Чаще всего: опечатка в конфиге. Исправь и повтори. Файл можно просто
удалить и вернуться к парольному входу:

```bash
sudo rm /etc/ssh/sshd_config.d/10-strict.conf && sudo systemctl restart ssh
```

### «Скрипт упал на середине — что уже сделано?»

Безопасная логика скрипта: каждый шаг — только после бэкапа. Проверь:

```bash
ls ~/.ssh/            # есть .bak.<число>? значит бэкап прошлого состояния есть
sudo cat /root/.ctf_passwd_backup   # новый пароль записан сюда
```

Просто продолжи с шага, на котором остановился (все шаги независимы и
повторяемы).

### «Я запер себя снаружи»

Правило из §4 применялось и всё равно заперся (например, потерял ключ):

- **не выключай машину** — твоя сессия внутри ещё может быть жива;
- если сессия жива: верни бэкап ключей/конфига (команды выше);
- если сессии нет: у виртуалки есть **консоль** (окно VM / VNC-доступ) —
  это локальный вход, он не зависит от ssh. Зайди через неё и чини.

---

## 4. Три железных правила (выучи их)

1. **Не закрывай рабочую сессию, пока не проверил другой способ входа.**
   Это единственная причина, по которой люди запирают себя.
2. **Каждое изменение — с бэкапом.** Одна команда `cp file file.bak`
   превращает любую ошибку из катастрофы в откат.
3. **Порядок: пароль → ключ → проверка ключа → и только потом строгость.**
   Никогда не выключай пароль, не проверив ключ.
