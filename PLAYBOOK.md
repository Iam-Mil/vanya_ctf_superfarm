# PLAYBOOK — InnoCTF Junior, финал (Attack-Defense, ForcAD)

Один файл, по которому живёт вся команда завтра. Всё сверено с кодом ForcAD
(актуальная версия из письма) и с инфраструктурой из рассылки оргов.

---

## 0. Параметры игры (из письма оргов) и что они значат

| Параметр | Значение | Что это значит на практике |
|---|---|---|
| Раунд | **2 минуты** | чекер каждые 2 мин прогоняет check→put→get по всем командам |
| Флагов на уязвимость | **2** | в каждый сервис каждый раунд кладётся 2 свежих флага |
| Flag lifetime | **5 раундов = 10 минут** | стыренный флаг нужно сдать в течение 10 минут после укладки |
| Hardness | **10** | кража при равных силах ≈ **+79 атакующему / −79 жертве**; разброс ~50–110; максимум ~158 |
| Score | **2500** | стартовый счёт за каждый сервис, Elo перетекает между командами |
| Формат флага | `[A-Z0-9]{31}=` (дефолт ForcAD) | 31 символ A-Z/0-9 и `=` в конце, первая буква = первая буква имени сервиса |

Скорость: каждый сервис у каждой команды держит ~10 живых флагов
(2/раунд × 5 раундов). Один флаг засчитывается **одной** команде — кто
первый сдал, тот и получил очки (`Flag already stolen` остальным).
Первый сдавший по уязвимости = **first blood**, фиксируется отдельно.

Очки за защиту напрямую не начисляются: `score` меняется только кражами.
Но DOWN-сервис — это: новые флаги не кладутся (нечего защищать), красный
статус на борде для всех, и если орги включили `volga_attacks_mode` — ваши
сдачи флагов по этому сервису не примут вообще («Cannot submit flags while
service is down»). Так что держать сервисы живыми — приоритет №1.

## 1. Сеть и её главная фишка

```
ваша команда X:
  10.2.X.0/24 — подсеть
  10.2.X.1    — шлюз
  10.2.X.2    — ваш vulnbox
  Kali-машины — остальные IP подсети (записать IP каждого!)

жюри: 10.10.10.10
  :80    — scoreboard + API + приём флагов (PUT /flags)
  :8080  — прокси во внешний интернет (HTTP GET, allowlist, свой сертификат)

цели: 10.2.Y.2 — vulnbox команды Y
```

**Весь межкомандный трафик идёт через шлюз и виден как `10.2.X.1`.**
Следствия (важно, это меняет стандартные приёмы):

1. **По IP не атрибутировать никого** — в логах все атаки с одного адреса.
   «Кто нас ломает» — только по содержанию трафика (tcpdump), не по IP.
2. **Банить IP атакующих бессмысленно** — забанишь шлюз, положишь всё.
   Не банить `10.2.X.1` ни при каких условиях.
3. **SSH фильтровать точными IP ваших Kali**, не подсетью — шлюз тоже
   внутри подсети, whitelist `10.2.X.0/24` откроет SSH всему миру.
4. Чекер жюри, скорее всего, тоже приходит через `.1`: иначе вся защита
   сводилась бы к бану шлюза («забанил .1 — ты неатакуем») — орги такую
   дырку не оставили бы. Точно узнаём tcpdump'ом в Т0+10 (2 раунда
   наблюдения). `.1` не трогаем ни при каких условиях: если чекер через
   него — бан = мгновенный DOWN всех сервисов.
5. Прокси-сервер: всё внешнее качаем ЗАРАНЕЕ (сегодня), на игре через
   GET-only-прокси можно только читать — docker build / pip install на
   месте скорее всего не пройдут.

## 2. Стек команды: что используем

### Основной вариант (рекомендуемый, всё от оргов)

```
Капитан (одна из Kali amd64):
  docker (apt install docker.io docker-compose-v2 — ставится на месте)
  S4DFarm  :5137  — ферма: команды, статистика, сдача флагов в жюри
  neo      :5005  — сервер: раздача сплойтов на все Kali команды

Атакующие (каждая Kali):
  neo client (tools/neo_client_2.4.2_linux_amd64.tar.gz — без docker,
              нужен только python3 + requests)
                     флаги отдаёт в ферму

Защитник:
  SSH на vulnbox  — harden.sh, патчи, бэкапы, iptables
```

Схема потока: сплойт написан → `neo add` (ушёл всем клиентам сам) →
клиенты гонят его каждые N минут по своей части команд → флаги в ферму →
ферма пачками ≤100 сдаёт в жюри `PUT http://10.10.10.10/flags` с вашим
`TEAM_TOKEN` (протокол `forcad_http.py` из этого пакета).

### Запасной вариант (если docker на Kali не взлетит)

`thrower.py` на каждой Kali + ручное разделение команд между атакующими
(никогда не бегайте по одному и тому же списку вдвоём — второй сдаст
только `Flag already stolen`). Работает вообще без инфраструктуры.

## 5. Атака: как искать и писать сплойты

1. **attack_data** (`GET /api/client/attack_data/`) — если сервис pfr
   (у C4T-игр почти всегда так), там публичные flag ids: `route_id`,
   `post_N`, usernames. Это готовая карта «где лежит флаг».
2. **Поведение чекера** = спецификация сервиса. Чекер `put` кладёт флаг
   через пользовательский сценарий (register → create note → ...).
   Повторите его руками на своём боксе: что создалось, что видно анониму,
   что видно другому юзеру. Дырка обычно: «объекты доступны без авторизации
   / по перебору id / насквозь через инъекцию».
3. **Читать код** на Kali (не на боксе): grep по роутам, auth-декораторам,
   SQL-запросам, `eval/exec/deserialize`, секретам в конфигах.
4. Референс-паттерны — на публичных гитхабах оргов (ссылки в их письме):
   слепой перебор — `C4T-BuT-S4D/innoctf-final-10-05-2020` → sploits/divnik;
   attack_data+XXE+JWT — `C4T-BuT-S4D/ctfcup-2023-ad` → sploits/explorers.

Свой бокс = полигон: поднять сервис локально в docker на Kali, гонять
сплойт на `127.0.0.1`, и только потом `neo add`.

## 6. Защита: как патчить не убив чекер

Железное правило: **один патч → проверка → следующий**. Никаких
«перепишем половину сервиса разом».

1. `cp app.py app.py.bak.$(date +%s)` (или git init в каталоге сервиса)
2. Правка минимальная: закрыть дырку, не менять поведение для чекера
   (чекер ходит теми же ручками, что и в 1-м пункте атаки!)
3. Если сервис в docker: пересборка/рестарт, проверить `docker ps` (не
   restart-loop) и руками открыть главную страницу
4. 3 раунда (6 минут) смотреть статус на борде. Не OK — мгновенный откат
   из бэкапа, думать дальше.

Что закрывать в первую очередь — по очереди:
- дырки, по которым вас уже сливают (видно по логам фермы: с кого берут)
- дырки, которые вы сами нашли у себя (= они есть у всех, все будут вами)
- «бесплатные» уязвимости из attack_data (если нашли вы — найдут и вас)

## 7. Типичные ошибки (собраны с прошлых игр + наша специфика)

1. **Забанить шлюз `10.2.X.1`** → отрезали игровой трафик и, скорее всего,
   чекер: мгновенный DOWN всего, что у вас есть.
2. **Whitelist SSH по подсети** → открыли SSH всем командам (шлюз в подсети).
3. Выключить парольный SSH, не проверив вход по ключу → потеряли бокс.
4. Патч сломал чекер → DOWN на борде; без бэкапа → долгий откат.
5. Двое атакуют один список команд → второй сдаёт `already stolen` впустую.
6. Свалить >100 флагов за один PUT / долбить >2 запросов/с → 429, флаги
   сгорают (у них окно всего 10 минут).
7. Забыть про 10-минутное окно флага: сплойт раз в 15 минут = половина
   флагов протухает. Интервал сплойта ≤ 2 минут (раунд).
8. Тестировать сплойт только на свежем локальном сервисе — на живых боксах
   данные другие, сплойт падает. Обрабатывать исключения, не падать, в
   stderr писать диагностику (ферма её покажет).
9. Качать docker/pip на игре через GET-only-прокси → всё тяжёлое качаем сегодня.

## 8. Первая помощь

| Симптом | Что делать |
|---|---|
| Борда красная по сервису | `docker ps` на боксе → рестарт не помог → откат последнего патча |
| Флаги не принимаются вообще | проверить `TEAM_TOKEN`; посмотреть ответ thrower/фермы: `Game is not available` = игра не стартовала; `service is down` = volga-режим, подними свой сервис |
| neo-клиент не подключается | `--host <ip_капитана>:5005` совпадает, `grpc_auth_key` одинаковый у всех |
| Ферма сдаёт, всё отвергнуто | формат флага в config фермы ≠ реальному (`[A-Z0-9]{31}=`), посмотреть на живой флаг глазами |
| Не зайти на бокс | пароль могли сменить не вы → console/VNC-доступ к VM, оттуда восстановить ключи |
