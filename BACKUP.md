# BACKUP.md — бэкапы на Attack-Defense: как, когда и что восстанавливать

Почему это критично на игре — три реальные беды, от которых спасает бэкап:

1. **Твой же патч сломал чекер** → статус DOWN, очки капают мимо. Нужен откат
   за секунды, а не «ща вспомню, что менял».
2. **Другая команда wipe'нула данные твоего сервиса** (это нормальная атака) →
   без копии базы ты не восстановишься до конца игры.
3. **Бокс умер/его уронили** → всё, что лежало только на нём, погибло.

---

## 1. Три уровня бэкапа — и когда какой

| Уровень | Команда | Когда | Зачем |
|---|---|---|---|
| **Микро** | `sudo ./backup.sh snap <файл>` | перед КАЖДЫМ изменением файла | откат своей ошибки за 1 секунду |
| **Полный** | `sudo ./backup.sh create <имя>` | T0 («pristine»), после больших правок, раз в час-два | эталон + восстановление после чужой атаки |
| **Копия на Kali** | `rsync ...` (скрипт печатает её сам) | сразу после каждого `create` | бэкап умирает вместе с боксом — копия обязана жить и у тебя |

Запомни порядок дня: **pristine при получении бокса → snap перед каждым
патчем → create по вехам → rsync на Kali каждый раз**.

---

## 2. Полный расклад по дню

```bash
# T0 — получили бокс. ДЕВСТВЕННЫЙ СНАПШОТ (один раз, не пропусти!):
sudo ./backup.sh create pristine

# ...защита (SECURE.md), разведка, нашёл уязвимость, патчишь:
sudo ./backup.sh snap /opt/service/src/app.py     # ← ВСЕГДА перед правкой
nano /opt/service/src/app.py                       # правишь
docker compose up --build -d                       # применяешь
# статус на борде красный? откат:
cp /opt/service/src/app.py.bak.* /opt/service/src/app.py

# после каждого большого этапа (закрыли 2 дырки, поменяли конфиг nginx...):
sudo ./backup.sh create
rsync -av root@10.2.X.2:/root/backups/ ~/vb_backups/    # ← НА КАЛИ, обязательно
```

## 3. Что `create` кладёт в архив

```
<имя>_<дата>.tgz
├── manifest.txt           — вывод docker ps (что вообще работало)
├── containers.json         — docker inspect ВСЕХ контейнеров (карта «как было»)
├── sources_and_configs.tar — исходники (/opt /srv /var/www) + nginx/systemd/cron
│                             + все docker-compose.yml на диске
├── volumes/               — ДАННЫЕ: bind-монтирования + docker-тома (postgres/mongo)
└── dbdumps/               — pg_dumpall / mongodump (если контейнеры БД живы)
```

Архив лежит в `/root/backups/`. Если в выводе были жёлтые `[!]` — не страшно:
это значит «какой-то кусок не собрался» (например, нет mongo), остальное
в архиве есть. Красный `[X]` — только если создать архив не вышло совсем.

**Размер:** обычно десятки–сотни МБ. Если архив распух до гигабайт —
смотри, не собираются ли туда тяжёлые логи (`/var/log` мы не берём).

## 4. Как восстанавливать — по сценариям

### Сценарий А: «мой патч сломал чекер» (самый частый, 90% случаев)

```bash
ls /opt/service/src/app.py.bak.*       # найти свой микро-бэкап
cp /opt/service/src/app.py.bak.1732... /opt/service/src/app.py
docker compose up --build -d           # пересобрать с откачанным файлом
```
Откат занимает ~30 секунд. Именно для этого `snap` перед каждой правкой.

### Сценарий Б: «сломал, а snap не делал» — вытащить файл из архива

```bash
sudo ./backup.sh restore /root/backups/pristine_....tgz
# распакует в /root/restore_*/ (живое НЕ трогает!) и подскажет:

# посмотреть, что внутри:
tar tf /root/restore_*/sources_and_configs.tar | grep app.py

# вернуть один файл на место (перезапишет текущий!):
tar xf /root/restore_*/sources_and_configs.tar -C / путь/к/app.py
docker compose up --build -d
```

### Сценарий В: «нам wipe'нули базу»

Данные лежат в `volumes/*.tgz` архива. bind-архивы содержат исходные пути:

```bash
sudo ./backup.sh restore ~/vb_backups/<архив>.tgz
tar xzf /root/restore_*/volumes/bind_opt_service_db.tgz -C /
# (посмотрел имя файла через: tar tzf ... | head)
# если это был docker-ТОМ (не bind): вернуть через alpine-контейнер —
# команда печатается при restore
docker compose up -d --force-recreate <сервис>
```

### Сценарий Г: «бокс погиб полностью»

Самый страшный — но у тебя есть копия на Kali:

```bash
# на живом/новом боксе:
rsync -av ~/vb_backups/ root@<ip_нового_бокса>:/root/backups/
sudo ./backup.sh restore /root/backups/pristine_....tgz
# дальше по напечатанной инструкции: развернуть исходники и данные,
# затем поднять сервисы:
cd /opt/service && docker compose up --build -d
```

## 5. Если скрипт не работает — всё руками (простые команды)

```bash
# микро-бэкап файла:
cp -a app.py app.py.bak.$(date +%s)

# полный архив каталогов:
sudo tar czf /root/my_backup.tgz /opt /srv /etc/nginx

# дамп postgres руками (имя контейнера из docker ps):
docker exec <pg-контейнер> pg_dumpall -U <юзер> | gzip > /root/pg.sql.gz

# стянуть на Kali:
rsync -av root@10.2.X.2:/root/my_backup.tgz ~/vb_backups/

# распаковать:
tar xzf my_backup.tgz -C /         # поверх (аккуратно!)
tar xzf my_backup.tgz -C /tmp/look # просто посмотреть
```

## 6. Привычки и типичные ошибки

| Ошибка | Правильно |
|---|---|
| бэкап только на боксе | **всегда** rsync на Kali сразу после create |
| первый бэкап «когда-нибудь потом» | pristine в первые минуты, ДО любых изменений |
| править файл без snap | `snap` перед каждой правкой — рефлекс |
| восстановить «на глазок» поверх | `restore` сначала в отдельный каталог, потом осознанно |
| забыть про dumps при живом postgres | `create` сам пробует pg_dumpall — просто не пропускай шаг |

И связка с другими гайдами: `SECURE.md` (защитить бокс) → этот гайд
(зафиксировать состояние) → `SPLOITS.md`/`FARM.md` (атака). Порядок
завтрашнего утра именно такой.
